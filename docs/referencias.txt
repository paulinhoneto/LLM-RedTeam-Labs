padrão de arquitetura de uma SPA moderna (Single Page Application) que usa um sistema de escopos (scopes) para carregar configurações específicas.

2. O parâmetro did (Device ID)
parâmetro did (Device ID)
Note o did=558a08f1-568d-483c-b795-53497dc01d01. Esse é o Device ID, um identificador único do seu navegador/dispositivo. Ele é enviado em todas as requisições de configuração. É um dado sensível? Sim, ele identifica o seu dispositivo. Se você alterar esse did para o de outra pessoa, o servidor pode retornar as configurações daquela pessoa? Teste isso. (Se o servidor não validar a propriedade do did, pode ser um vazamento de configurações).

3. Os Escopos (scope)

Você encontrou quatro endpoints diferentes:

scope=main: Configurações gerais da conta.
scope=web_upgrade: Provavelmente configurações de plano/assinatura (upgrade).
scope=provider: Configurações do provedor (talvez relacionado ao Google OAuth).
model: Configurações de modelo (qual modelo a IA está usando).

sso mostra que o backend separa as responsabilidades. Cada escopo tem sua própria lógica de validação.

🛡️ O que são esses dois tokens?
   Authorization: Bearer e o x-settings-token
   
   DeepSeek implementou uma camada extra de segurança (defesa em profundidade).
   
Authorization: Bearer <token>: 

* Este é o token padrão de autenticação (OAuth2/JWT). Ele prova quem você é (sua identidade). Sem ele, o servidor não sabe que você está logado via Google.
* Ele geralmente tem um tempo de vida curto e é enviado em todas as requisições

 x-settings-token: <token>:

* Este é um Token de Contexto (ou Token de Capacidade / CSRF Token customizado). Ele prova que você tem permissão para acessar 
  aquele escopo específico (main, model, web_upgrade, etc.) naquele momento.

* Por que a DeepSeek usa isso? Para mitigar CSRF (Cross-Site Request Forgery) e vazamento de escopo. 
  Se um atacante roubar apenas o Bearer Token (ex: via XSS), ele pode não conseguir alterar as configurações do modelo 
  se não tiver o x-settings-token correspondente.



OAuth 2.0 for Native AppsRFC 8252 
- obrigatoriamente implementar ao fluxo
  - PKCE (Proof Key for Code Exchange)

Exigências:  

- "Public native app clients MUST implement the Proof Key for Code Exchange (PKCE) extension to OAuth"  - RFC 8252, Seção 6.
   PKCE obrigatório para apps nativos 

Ou seja: se você está fazendo um app nativo (público) com OAuth 2.0, você não pode implementar o OAuth "puro". 
Você é obrigado a acoplar o PKCE ao fluxo

Não são duas implementações separadas; é uma implementação de OAuth 2.0 que inclui o PKCE como parte inseparável do fluxo de código.

A Falha da CVE-2020-7692 (Google OAuth Client)

A descrição da CVE é precisa: "PKCE support is not implemented in accordance with the RFC for OAuth 2.0 for Native Apps" .

Isso significa que a biblioteca não fazia a verificação de posse que o PKCE exige. Sem o PKCE funcionando, o código de autorização que volta para o app é apenas um "bilhete" que qualquer app malicioso no mesmo dispositivo pode interceptar (via registro do mesmo esquema de URI) e trocar por um token de acesso 

A falha não é "ter PKCE mas mal". A falha é que a biblioteca não implementava a proteção do PKCE de forma alguma (ou de forma incompleta), deixando o código de autorização vulnerável a interceptação.
O atacante rouba o código e o usa antes do app legítimo, porque o servidor de autorização não tem como distinguir quem está trocando o código .

Implementação Modelo Resumida (RFC 8252 + PKCE)

Aqui está o fluxo mínimo que um bug hunter precisa reconhecer como correto:

Passo 1: O App gera o code_verifier (segredo local)
O app cria uma string aleatória longa (43-128 caracteres). Isso nunca sai do app.

Passo 2: O app calcula o code_challenge
code_challenge = BASE64URL(SHA256(code_verifier)) . 

Passo 3: O app abre o navegador com a URL de autorização 

https://servidor.com/authorize?
  response_type=code
  &client_id=app_id
  &redirect_uri=com.app:/callback
  &code_challenge=XYZ123... (o hash)
  &code_challenge_method=S256

O que obersvar aqui : response_type=code (nunca token). presença de code_challenge e 
code_challenge_method=S256 . 

Passo 4: O usuário autoriza e o navegador redireciona de volta
com.app:/callback?code=ABC456

O app recebe apenas um codigo temporário. nehum token aparece aqui 

Passo 5: O app troca o código por um token (nos bastidores)
O app faz um POST para o servidor de token enviando:

- o code recebido 
- o code_verifier original (o segredo do Passo 1)

Passo 6: o servidor valida 
o servidor pega o code_verifier recebido, aplica SHA256, e compara com o code_challence que ele guardou no passo 3.
se baterem, ele emite o token. se não baterem, ele nega 

Por que o blue team derrata o bule red ? 
se um app malicioso interceptar o code no Passo 4 (via URI scheme), ele não terá o code_verifier que o app legitimo
gerou no Passo 1. quando ele tentar trocar o codigo por um outro token no Passo 5, servidor vai negar, porque
o hash do que ele enviar (ou a ausência do verifier) não corresponderá ao code_challenge original. 

O fluxo implicito é inseguro por design porque pula os Passos 1, 2, 3 (parcialmente) e 5. ele devolve o token 
diretamente no Passo 4 ( response_type=token ), na URL. como não ha troca de código, não há onde aplicar o PKCE. 
o  token é roubado diretamente da URL se interceptado .

como identificar no mundo real (Bug Hunter)
Olhe para a URL de autorização que o app abre: 

característica                    correto (RFC 8252 + PKCE)                 Inseguro/Implicoto 
response_type                     code                                      token ou id_token token 
code_challenge                    presente                                  ausente
code_challenge_method             S256 (ou plain)                           ausente
volta no redirect                 ?code=...                                 #access_token=...  


Se você interceptar o redirect e ver um access_token na URL, o app está usando fluxo implicito 
(ou hibrido Inseguro). Se vc ver um code mas não houver code_challenge na URL inicial, o PKCE não esta sendo usado, e aquele code é roubável

JWS(RFC 7515) 
- define formato e o mecanismo de verificação de assinatura do JWS (JSON Web Signature) 

JWT(RFC 7519) 
- é uma aplicação concreta do JWS. A assintautra JWT que vejo é essencialmente um objeto JWS.

Posicionamento Central do RFC 7515
- o RFC 7515 especifica como assinar digitalmente o conteúdo no formato JSON (ou protegê-lo com HMAC). 
  garantindo integridade e autenticidade dos dados. Ele define: 

  -  Estrutura JWS: Consiste em três partes—Protected Header, Payload e Signature—conectadas por pontos (.), 
     sendo esta a forma padrão dos JWT.

  -  Papel do parâmetro alg: No cabeçalho (Header), alg especifica o algoritmo usado para assinar 
    (como RS256, HS256), sendo um dos campos mais críticos para a segurança.

Relação com JWT

JWT (RFC 7519) é uma "carga útil de declarações" transportada usando a estrutura JWS. Quando você decodifica a primeira parte de um JWT (Header), vê algo como {"alg": "RS256", "typ": "JWT"}—isso é exatamente o Protected Header do JWS. Portanto, entender o RFC 7515 é entender como a assinatura JWT é gerada e verificada.


Ponto de Entrada para Testes de Segurança (Caça de Bugs)

Como pesquisador de segurança, ao auditar JWT, o núcleo é verificar se a implementação de verificação de assinatura do JWS (RFC 7515) está rigorosa. As falhas comuns incluem:

- Ataque alg: none: Se o servidor aceitar tokens JWT com alg definido como none e assinatura vazia, um atacante pode forjar qualquer identidade. Houve um caso em que o Authlib falhou ao rejeitar alg: none, causando bypass de autenticação; a Microsoft Titan também sofreu com falha na verificação de assinatura, permitindo que um pesquisador falsificasse um administrador e recebesse uma recompensa de $5.000.

- Ataque de confusão de algoritmo: Se o servidor suportar simultaneamente algoritmos simétricos (HMAC) e assimétricos (RSA), um atacante pode alterar alg para HS256 e usar a chave pública (exposta publicamente) como chave secreta HMAC para forjar assinaturas, enganando o servidor.

- Sobrescrita de cabeçalho: Se a biblioteca der prioridade ao alg no cabeçalho não protegido (Unprotected Header) sobre o protegido (Protected Header), um atacante pode contornar a verificação alterando o cabeçalho não protegido.

Resumo em uma frase: O RFC 7515 é a "lei" das assinaturas JWT. Qualquer falha na verificação de assinatura (aceitar none, confusão de algoritmos, confiar erroneamente em cabeçalhos não protegidos) é uma violação das suas especificações, podendo levar diretamente a bypass de autenticação ou escalação de privilégios.

RFC 7517 JWK 
- define o formato JWK (JSON Web Key), em termos simples, ele especifica como usar o formato JSON para representar
  uma chave criptografica (geralmente chave pública)

JWK 
um objeto json que descreve os detalhes de uma chave. por exemplo, para uma chave publica RSA, ele contem o modulo
n, o expoente e, o tipo de chave kty (como "RSA"), o identificador da chave kid, etc.


JWK Set (JWKS):
É um array JSON chamado keys, que contém um conjunto de JWKs. Geralmente, o servidor de autenticação fornece um endpoint JWKS onde o aplicativo cliente pode buscar todas as chaves públicas usadas para verificar assinaturas .

Para que serve: A função mais comum é verificar a assinatura de um JWT. O servidor usa sua chave privada para assinar o JWT; o cliente ou servidor que recebe o JWT usa a chave pública no formato JWK publicado no endpoint JWKS para verificar se a assinatura é válida
